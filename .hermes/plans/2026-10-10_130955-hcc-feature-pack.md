# hcc Feature Pack — Implementation Plan

> **For Hermes:** plan-only turn. No implementation. Execute task-by-task later.

**Goal:** Turn home-control-center from a static dashboard into an editable, monitoring-capable, extensible control center — (1) editable home layout, (2) more widgets, (3) real monitoring, (4) advanced mode, (5) Uptime Kuma integration.

**Architecture:** All five features ride on the existing Next.js 15 App Router + server-actions architecture. No new tables for (1) — layout lives in the existing `settings` key/value table. Widgets become a registry so (1) edit mode and (2) new widgets share one mechanism. Monitoring (3) needs no schema change either (`services`, `metrics`, `alerts` already exist) — it needs data + transition logic. Uptime Kuma (5) is read-only HTTP against Kuma's status-page JSON.

**Tech Stack:** Next.js 15.5.23 (App Router, `output: "standalone"`), React 19, NextAuth v5 beta (JWT), Prisma + MySQL 8, Tailwind v4, framer-motion, recharts, Zod, TanStack Query.

## Phase 2 — "home edit": editable dashboard layout

### Task 2.1: Persist layout in `settings` (no migration)

**Objective:** Store widget order + hidden set per user.

**Files:** Create `src/actions/layout.ts`; modify `src/lib/validators.ts`.

**Code:**
```ts
// src/actions/layout.ts
"use server";
import { auth } from "@/lib/auth";
import { prisma } from "@/lib/prisma";
import { z } from "zod";
import type { ActionResult } from "@/types";

const layoutSchema = z.object({
  order: z.array(z.string()).max(64),
  hidden: z.array(z.string()).max(64),
});

export async function getLayout() {
  const session = await auth();
  if (!session) return null;
  const row = await prisma.setting.findFirst({
    where: { key: "dashboard_layout", userId: session.user.id },
  });
  if (!row) return null;
  try { return layoutSchema.parse(JSON.parse(row.value)); } catch { return null; }
}

export async function saveLayout(input: unknown): Promise<ActionResult> {
  const session = await auth();
  if (!session || (session.user as { role: string }).role !== "ADMIN")
    return { success: false, error: "Unauthorized" };
  const parsed = layoutSchema.safeParse(input);
  if (!parsed.success) return { success: false, error: "Invalid layout" };
  await prisma.setting.upsert({
    where: { key_userId: { key: "dashboard_layout", userId: session.user.id } },
    create: { key: "dashboard_layout", value: JSON.stringify(parsed.data), userId: session.user.id },
    update: { value: JSON.stringify(parsed.data) },
  });
  await prisma.auditLog.create({
    data: { userId: session.user.id, action: "UPDATE_LAYOUT", details: JSON.stringify(parsed.data) },
  });
  return { success: true, message: "Layout saved" };
}
```
> **Confirmed:** `Setting` is `@@map("settings")` with `@@unique([key, userId])` (`prisma/schema.prisma:302-313`), so `prisma.setting.upsert({ where: { key_userId: { key, userId } } })` is valid as written.

**Verify:** build; then a temporary settings page button calls `saveLayout` and `getLayout` returns it.
**Commit:** `feat(dashboard): persist layout in settings`

## Risks / tradeoffs / open questions

1. **`Setting` uniqueness** — Task 2.1 assumes `@@unique([key, userId])`. Verify at `prisma/schema.prisma:302` before writing the `upsert`.
2. **No tests** — every gate is `npm run build` + a manual/curl check. Acceptable per repo convention (AGENTS.md: "Tests: None"), but it means regressions are caught by eye.
3. **SSRF guard** — LAN/own-host targets must be in `ALLOWED_INTERNAL_HOSTS` or monitoring silently reports failures. This is the most likely cause of "why is nothing monitored".
4. **Alert storms** — a flapping service would alert every transition. Consider requiring 2 consecutive failures before OFFLINE (add a `failureCount` or use `Metric` history) — decide before Task 3.4.
5. **`revalidate = 10` vs polling** — Phase 1/2 widgets add server-side fetches (weather, Nextcloud, docker). With `revalidate = 10` each dashboard hit can fan out to 6+ upstreams every 10 s. Consider moving to per-widget React Query with longer `staleTime` (the `POLLING_INTERVALS` map already encodes intended cadences).
6. **Scope creep** — Phases 1 and 5 are open-ended ("make more", "kum"). Recommend shipping Phase 0 + 3 first (they fix real breakage), then 1, 2, 4, 5.
7. **"kum" is a guess.** Confirm before Task 5.2 — it could mean something else entirely.
